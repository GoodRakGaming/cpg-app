# Контекст для сессии дизайна КП (Phase 9)

Это самодостаточный бриф для нового чата. Задача этого чата — **не писать код**, а
проанализировать реальные образцы КП и спроектировать единый минималистичный визуальный
стиль, который потом реализует разработчик (в основном чате проекта).

---

## Проект

Commercial Proposal Generator — веб-приложение для создания и генерации PDF коммерческих
предложений (КП). Backend на Node.js/Express/Sequelize/PostgreSQL, PDF рендерится через
Puppeteer (headless Chrome) из HTML/CSS-строки. Развёрнуто в проде: `cp.profstroi74.ru`.

## Задача этой сессии

Сейчас КП создаются вручную (Word/Excel/PDF) в стиле, который ожидает заказчик. Сгенерированный
приложением PDF выглядит иначе — обобщённый шаблон без реквизитов, логотипа, разделов и подписей
(тёмно-синяя шапка, плоский список позиций). Нужно:

1. **Проанализировать приложенные образцы** реальных КП (пришлю файлы отдельно) — вычленить
   структуру: какие блоки есть всегда, какие опциональны, порядок, что визуально важно
   (иерархия, акценты), что можно упростить
2. **Спроектировать один минималистичный унифицированный стиль**, который заменит и текущий
   generic-шаблон, и ручное создание — не копия образцов один-в-один, а чистая переработка в
   единую систему (цель — минимализм, а не декоративность)
3. Отдать результат в формате, который можно **напрямую передать разработчику** (см. "Что нужно
   на выходе" ниже) — этот чат не имеет доступа к кодовой базе и не пишет код

## Технические ограничения (важно для дизайна)

- Результат рендерится **Puppeteer из чистого HTML + inline/embedded CSS** в PDF формата A4.
  Никакого JS, никаких внешних сетевых запросов (шрифты/логотип нужно либо считать безопасными
  веб-safe шрифтами, либо предполагать base64-embed для изображений)
- Размеры и отступы должны быть в PDF-дружественных единицах (mm/pt), с расчётом на печать —
  это не адаптивная веб-страница
- Итоговый макет должен быть готов лечь почти "как есть" в шаблонную строку HTML на backend —
  чем ближе черновик к финальному чистому HTML/CSS, тем меньше переделок

## Что уже решено по модели данных (не переизобретать)

- **Юрлицо = шаблон.** У приложения уже есть сущность "Template" — вместо отдельного профиля
  компании, реквизиты/логотип/подпись каждого юрлица будут жить в данных шаблона. Один шаблон =
  один визуальный/юридический профиль. Пользователь просто выбирает нужный шаблон при создании КП.
- Текущая структура данных (то, что уже есть и от чего отталкиваемся, не строго финально):
  - `Template.data`: `{ items: [...], terms, footer }` — базовые позиции-по-умолчанию, условия,
    футер
  - `Proposal.data`: `{ items: [...], description }` — позиции конкретного КП, описание
  - `item`: `{ name, description, quantity, price }`
- Это будет расширено (в рамках этой сессии — решить, чем именно): реквизиты компании
  (название, ИНН/ОГРН, адрес, контакты, банковские реквизиты), логотип, данные подписанта,
  группировка позиций по разделам

## Что нужно решить в этой сессии (открытые вопросы)

1. Точная структура разделов КП — что обязательно, в каком порядке (шапка, реквизиты, позиции,
   условия, подпись — и что ещё, судя по образцам)
2. Логотип на каждой странице PDF или только на первой/шапке
3. Формат подписи — текст (ФИО + должность) или изображение скана подписи
4. Как группировать позиции — по произвольным разделам с подзаголовками, по фиксированным
   категориям, или что-то другое, судя по образцам
5. Минимальный набор полей реквизитов, которые реально нужны (не тащить всё, что бывает в
   договорах, если в КП это не используется)

## Что нужно на выходе (для разработчика)

Пожалуйста, формируй финальный ответ так, чтобы его можно было отдать напрямую в реализацию:

1. **Готовый HTML/CSS-макет** — оформи как Artifact (самодостаточная HTML-страница, без внешних
   зависимостей). Размер A4, печатные единицы. Это должно быть по возможности близко к тому, что
   ляжет в `generateProposalHtml()` на backend
2. **Финальная структура данных** — конкретный JSON-shape для `Template.data` и `Proposal.data`
   после расширения (какие поля добавляются, куда именно — в шаблон или в конкретное КП)
3. **Явные ответы на 5 открытых вопросов** выше — не оставлять их открытыми
4. **Мини design-tokens** — шрифты (с учётом что это должны быть шрифты, доступные Puppeteer/
   Chromium без доп. установки, либо web-safe, либо чётко указать какой шрифт встраивать),
   цветовая палитра (минимум — 1-2 акцентных цвета, остальное нейтральные/серые тона, раз цель
   минимализм), отступы/сетка

## Рекомендованные skills для этой сессии

- **artifact-design** — обязательно перед тем как строить HTML-макет. Даёт методологию
  элегантного дизайна страниц (типографика, цвет, сетка, консистентность), подходит прямо для
  задачи "получить чистый профессиональный HTML-документ"
- **dataviz** — пригодится конкретно для таблицы позиций/цен (основной содержательный блок КП):
  выравнивание чисел, иерархия итоговой строки, консистентные отступы в табличных данных — там
  есть готовые паттерны именно под это

Если увидишь в списке доступных скиллов что-то более подходящее под "разбор образцов документов
и построение единого стиля из них" — используй по своему усмотрению, эти два не единственно
возможные, просто наиболее очевидно релевантные из известных на момент написания этого брифа.
