**Официально не существует в библиотеке Ollama**: `gigachat3` (голый тег) — GigaChat есть только под никами сторонних загрузивших пользователей (forzer/Bored/infidelis/second_constantine/evilfreelancer), официального тега от Sber/ai-sage нет.

**Важное наблюдение по единицам измерения**: разные модели/режимы возвращают "м2" и "м²" как разные строки — **обязательна нормализация юникода единиц измерения на этапе backend-валидации** (уже было заложено как открытый вопрос в исходном Phase 10 документе, тест подтвердил, что риск реальный).

**Проблема "does not support tools" в Open WebUI (решено)**: обе GigaChat-модели давали ошибку `does not support tools` при обычном текстовом запросе без явного использования инструментов. Причина — в карточке модели (Workspace → Models → редактирование) раздел **"Возможности"** по умолчанию включает кучу чекбоксов (Веб-Поиск, Встроенные Инструменты, Автоматизации, Календарь и т.д.), которые Open WebUI прикрепляет к запросу как `tools` — а community-конверты GigaChat не имеют объявленного tool-calling шаблона, поэтому Ollama отвергает запрос целиком. **Решение**: снять все галочки в разделе "Возможности" для этих моделей — после этого чат заработал штатно. На будущее: при добавлении новой модели в Open WebUI — сразу проверять этот раздел, если модель "не отвечает" без явной причины.

### OCR

| Модель | Роль | Статус |
|---|---|---|
| dots.mocr | основная — печатные документы, таблицы | не начато (скачать) |
| FireRed-OCR | альтернатива — тоже сильна на печати, сравнить bok-о-бок на реальных КП | не начато (скачать) |
| Qwen 3.5 4B | резерв — рукопись, сложные сканы, лучший локальный универсал | не начато (скачать) |

Решено: FireRed-OCR и dots.mocr тестируем оба на реальных документах пользователя (печать+таблицы), выбор — по факту, не по чужому бенчмарку.

**Правило по рукописи** (зафиксировано заранее): рукописные документы → всегда `pending_review`, без порогов автодоверия — локальные модели показывают низкую точность на рукописи по всем найденным тестам.

### Почему Q4, а не Q8 (зафиксировано решение)

Разница в точности Q4_K_M vs Q8 на бенчмарках — единицы процентов (~4%), не разы. Для нашей задачи (короткое структурированное извлечение, не творческое рассуждение) это не критично, а VRAM-бюджет жёсткий (16GB). Q8 для 20B-моделей не помещается целиком (нужен offload на CPU — замедление в разы). Держим все модели в одном кванте (Q4) для честного сравнения. Если по итогам теста на реальных документах точность конкретной модели окажется недостаточной именно из-за квантования — можно точечно поднять квант для неё, пожертвовав вторым слотом.

### Скрипт автоматического сравнения ✅ СОЗДАН И ПРОГНАН ОДИН РАЗ

Bash-скрипт `test_models.sh` (лежит у пользователя на контейнере 107, копия — см. чат) прогоняет единый тестовый промпт через `/api/generate` на всех 5 моделях, сохраняет ответ + метрики (токены, время генерации, загрузки) в `model_comparison_report.md`.

**Результаты первого прогона (25.07.2026):**

| Модель | Формат цены | Токенов/сек (генерация) | Загрузка модели |
|---|---|---|---|
| Qwen3-14B | ✅ число (350) | 42 | 61s |
| GLM-4-9B | ❌ строка ("350 руб") — **на этом прогоне хуже, чем в ручном CLI-тесте ранее** | 68 | 37s |
| gpt-oss-20b | ✅ число (350) | 79 | 139s |
| GigaChat3.1-10B (Bored) | ⚠️ строка ("350") | 111 | 42s |
| GigaChat-20B-A3B (infidelis, q4_0) | ⚠️ строка ("350") | 138 | 74s |

**КЛЮЧЕВАЯ НАХОДКА**: GLM-4-9B на автоматическом прогоне выдала цену строкой, хотя при ручном тесте в CLI ранее — выдавала число на том же промпте. Это не баг скрипта — **формат ответа LLM без принудительной схемы не гарантирован даже у одной модели от раза к разу** (стохастичность сэмплинга). Это главный практический аргумент за grammar-constrained decoding (`format` с JSON Schema в Ollama) вместо расчёта на промпт-инструкции — промпт снижает вероятность неверного формата, но не гарантирует его.

**Время загрузки моделей (37-139 секунд)** — GPU не хватает держать несколько 10-20B моделей одновременно резидентно, Ollama выгружает/загружает при каждом переключении. **Архитектурный вывод**: в проде для extraction-пайплайна держать одну "рабочую" модель постоянно резидентной, не переключать между разными моделями туда-сюда через n8n.

## Ключевые технические заметки (чтобы не забыть)

1. **CPU для контейнера 107**: сознательно оставлено 2 ядра — GPU-инференс почти не использует CPU, ядра важнее другим LXC/VM на хосте.
2. **Диск шаблонов vs диск контейнера**: шаблон ОС (~1GB) — не важно, HDD или SSD. Диск самого контейнера (300GB, веса моделей) — уже важен объём, HDD с 1.6TB свободного места предпочтительнее SSD с 48GB.
3. **При обновлении драйвера NVIDIA на хосте в будущем** — не забыть ставить именно `nvidia-kernel-open-dkms`, а не `nvidia-kernel-dkms`, иначе снова "No devices were found" на Blackwell-картах.
4. **RAM хоста**: 48GB суммарно (8×2 + 16×2 DDR4). Контейнеру 107 выделено 20GB — с запасом под загрузку весов и context/KV-cache, остальное остаётся для других LXC/VM (Nextcloud, n8n и т.д.) и самого хоста.
5. **Ollama API** — единая точка входа для чата, n8n-извлечения и будущей Office-интеграции (`http://<host>:11434/v1/...`, OpenAI-совместимый). OCR — отдельный шаг перед этим, не через LLM (точность чисел/таблиц у классического OCR выше, чем у мультимодальных LLM "на глаз").
6. **Карта контейнеров/IP (закреплены на роутере — фактически статические, несмотря на DHCP)**:
   - 107 (ollama) — `192.168.1.106`, порт 11434 → домен `ollama.profstroi74.ru`
   - 108 (openwebui) — `192.168.1.107`, порт 8080 → домен `ai.profstroi74.ru`
   - Доступ из интернета сознательно не открыт — используем существующий OpenVPN на роутере
7. **`systemctl edit <service>`**: правки пишутся **над** строкой `### Edits below this comment will be discarded` — всё, что ниже (закомментированная копия оригинального юнита), не применяется, это просто справка.
