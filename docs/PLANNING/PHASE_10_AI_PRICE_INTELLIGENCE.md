## Архитектура (предложение, требует подтверждения)

```
Nextcloud (папка "На анализ")
        │  появился новый файл
        ▼
   n8n workflow (триггер по Nextcloud)
        │  скачивает файл
        ▼
   OCR (если скан/картинка в PDF)
        ▼
   Локальный LLM (отдельная VM/LXC с GPU) — извлечение структурированных данных:
   { работа, ед.измерения, цена, категория, источник, дата, уверенность }
        ▼
   Очередь на проверку человеком (pending_review)
        │  ручное одобрение/правка
        ▼
   price_catalog (таблица в БД commercial_proposal_generator)
        ▼
   Proposal Editor подсказывает рыночную цену при добавлении позиции
```

## Ключевое архитектурное решение: где хранить price_catalog

**Рекомендация: та же PostgreSQL, что и commercial_proposal_generator** (новые таблицы), а не
отдельный сервис/БД — каталог цен является прямым дополнением к генератору КП, не независимым
продуктом.

n8n **не должен писать в БД напрямую** — вместо этого backend получает внутренний API endpoint
(например `POST /api/price-catalog/ingest`) с отдельным API-ключом для n8n. Причины:
- Валидация и нормализация (категории работ, единицы измерения, дедупликация) остаются в одном
  месте — backend, а не дублируются логикой внутри n8n-workflow
- n8n не хранит DB-креды — сам n8n у вас публично доступен через домен
  (`192.168.1.103:5678`, публикуется в интернет ради VK Callback API), это лишний вектор атаки,
  если конфиг workflow утечёт
- Логику дедупликации/матчинга категорий проще потом поменять в одном месте, не трогая workflow

**Более простая альтернатива для быстрого старта** (компромисс скорость/качество архитектуры):
n8n Postgres-нодой пишет напрямую в отдельную "грязную" таблицу `price_catalog_raw`
(без валидации на стороне backend), а отдельный периодический job в backend разбирает её
в чистый `price_catalog`. Можно начать с этого, а потом заменить на API-приём, если понадобится.

## Критичный риск: качество автоматического извлечения

OCR + LLM будут ошибаться: неверно распознанные числа, спутанные единицы измерения (шт/м²/м.п.),
неправильная категоризация работ. **AI-извлечённые записи не должны сразу попадать в рабочий
каталог** — обязательна очередь ручной проверки (`pending_review`) минимум на старте, пока не
накопится статистика точности извлечения и не будет понятно, каким категориям/источникам можно
доверять больше.

## Открытые вопросы

- **Источники документов** — свои старые КП, прайс-листы поставщиков, прайс-листы
  конкурентов, или смешанно (вы отметили: "ещё не решил"). Влияет на промпт для LLM и на то,
  нужна ли атрибуция источника при подсказке цены оператору.
- **Атрибуция источника** — стоит ли различать "наша историческая цена" от "цена конкурента"
  при показе подсказки в редакторе (вероятно да — это разные по смыслу ориентиры: одно
  показывает, что мы обычно берём, другое — с чем конкурируем)
- **Таксономия категорий работ** — фиксированный справочник категорий или свободная
  категоризация с последующей кластеризацией (embeddings + `pgvector` для похожих
  формулировок вроде "малярные работы" / "покраска стен")
- **Частота появления новых документов** — разовая загрузка исторического архива, или
  постоянный процесс (влияет на то, нужен ли троттлинг/очередь обработки)
- **Формат подсказки в редакторе** — фиксированная цена, диапазон (мин/макс/медиана),
  с указанием количества источников и их типа?
- **Кто выполняет ручную проверку** `pending_review` — нужен ли отдельный UI-экран, или
  достаточно простого списка с approve/reject

## Примерные шаги реализации

1. Зафиксировать источники документов и таксономию категорий (зависит от решений выше)
2. Развернуть локальный LLM-инференс (отдельная задача — GPU passthrough, VM/LXC)
3. Спроектировать схему `price_catalog` + `pending_review` — миграция
   (`backend/migrations/run.js`)
4. Backend: ingest API + endpoint получения рекомендованной цены по категории
5. n8n workflow: Nextcloud trigger → OCR → LLM extraction → ingest API
6. Простой UI для проверки `pending_review` записей (approve/reject/правка)
7. Интеграция подсказки цены в Proposal Editor (после Phase 9)
8. Пилот на небольшом наборе документов, оценка точности, донастройка промптов
