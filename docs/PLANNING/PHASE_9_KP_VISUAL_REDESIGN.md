# Phase 9: Визуальный редизайн КП

**Статус:** дизайн зафиксирован (см. раздел "Решения из дизайн-сессии" ниже), можно приступать
к реализации.
**Цель:** привести генерируемый КП (PDF) и модель данных к виду, который ожидает заказчик,
чтобы можно было полностью перейти с ручного создания на генератор.
**Порядок:** делается **до** Phase 10 (AI price intelligence) — сначала нужно, чтобы заказчик
уже мог пользоваться генератором.

---

## Почему это отдельная фаза, а не мелкая правка

Судя по обратной связи ("вид КП не соответствует тому, что заказчик ожидает"), проблема не в
мелких стилевых деталях, а в структуре документа: нынешний генератор (`pdfService.js`) собирает
плоский список позиций + сумму, без реквизитов, логотипа, разделов и подписей — то есть меняется
не только CSS, но и модель данных, backend и редактор.

---

## Что меняется

### 1. Модель данных

**Решено:** реквизиты компании-исполнителя живут не в отдельной сущности "профиль компании",
а в **`Template.data`** — существующий механизм шаблонов уже даёт нужную гибкость: разные
юрлица = разные шаблоны. Выбор юрлица при создании КП становится выбором шаблона, отдельная
сущность/таблица не нужна.

Расширение `Template.data`:
- Название компании, ИНН/ОГРН, юридический и фактический адрес, контакты
- Банковские реквизиты (если печатаются в КП)
- Логотип (файл, путь/base64 хранится в `Template.data`)
- Данные подписанта (ФИО, должность), возможно — скан подписи как изображение

Плюс расширение структуры позиций в `Proposal.data`:
- Позиции сгруппированы по разделам/категориям (не плоский список)
- Условия/сроки/гарантии как отдельные структурированные блоки, а не один текст

### 2. Backend

- Новая таблица не нужна — реквизиты и логотип живут в существующем `Template.data` (JSONB),
  отдельной миграции для этого не требуется
- Endpoint загрузки логотипа для шаблона (multipart, валидация типа/размера — переиспользовать
  паттерн из `PDF_STORAGE_PATH` для хранения загруженных файлов)
- Обновление `templateSchema` (`backend/src/validators.js`) под новые поля реквизитов/логотипа/
  подписи; `proposalSchema` — под структуру разделов позиций

### 3. PDF-шаблон (`backend/src/services/pdfService.js`)

Самая объёмная часть, полностью зависит от эталонного макета:
- `generateProposalHtml()` — переписать под новую структуру (разделы, шапка с реквизитами
  и логотипом, блок подписи)
- Логотип придётся встраивать как base64 в HTML (Puppeteer рендерит из строки, внешние URL
  логотипа означали бы сетевой запрос на каждый рендер PDF — надёжнее embed)
- Сохранить текущие фиксы (Buffer.from для Puppeteer v24+, RFC 5987 кодирование имени файла)

### 4. Frontend (редактор)

- Форма реквизитов/логотипа/подписи в **Template Editor** (`/dashboard/templates/[id]`) —
  не отдельная страница профиля компании
- Загрузка логотипа с превью
- Редактор позиций в Proposal Editor — группировка по разделам вместо плоского списка
  (нужно решить: drag&drop переупорядочивание — nice-to-have, не обязателен в MVP)
- Обновить `ProposalEditorPage` под новую структуру `data`

## Решения из дизайн-сессии

Все 5 открытых вопросов закрыты по итогам отдельного чата, разобравшего реальные образцы КП
заказчика ("Профстрой"). Ниже — итог.

### Структура документа (фиксированный порядок)

Шапка (реквизиты + логотип) → блок получателя → заголовок "Коммерческое предложение" + вводный
абзац → таблица позиций (с опциональными разделами/подытогами) → итоговая сумма → условия →
блок подписи/печати. Порядок один и тот же для всех КП; блоки без данных просто не рендерятся
(например, нет доп. реквизитов — блок не рисуется, а не рисуется пустым).

### Логотип

Только на первой странице, в шапке рядом с названием компании, небольшого размера (до ~28мм по
высоте) — не на весь разворот. На последующих страницах — тонкая шапка с кратким названием
и номером КП, без логотипа.

### Подпись

Текстовая версия (должность + ФИО на строке подписи) — обязательный минимум, работает без каких-
либо загруженных файлов. Если в шаблоне загружено реальное изображение подписи/печати — оно
накладывается поверх/рядом со строкой. Без реального скана печать не имитируется декоративно —
либо настоящий скан, либо просто текст "м.п.".

### Группировка позиций

Произвольные разделы (не фиксированный справочник категорий) — у каждой позиции опциональное
поле `section`. Если поле заполнено хотя бы у части позиций — перед первой позицией раздела
рендерится подзаголовок + подытог по разделу. Если поле не используется ни у одной позиции —
обычная плоская таблица без подзаголовков. Общий итог — один раз, в конце, всегда.

### Минимальный набор реквизитов

Обязательно (рендерится всегда, если заполнено в шаблоне): название компании, юридический адрес,
ИНН, телефон/email. Опционально (отдельный блок, рендерится только если хотя бы одно поле
заполнено): ОГРН, КПП, банковские реквизиты — во многих реальных образцах их вообще нет.
Договорные реквизиты (не относящиеся к КП) — не нужны.

### ⚠️ Отложенный краевой случай — НЕ реализовывать пока

Часть КП (установка окон/дверей) сопровождается многостраничным (до ~35 стр.) приложением из
стороннего конфигуратора с детальной технической спецификацией по каждому изделию. **Это
приложение не воспроизводится в таблице позиций генератора** — строка в таблице остаётся одной
строкой с итогом (например: "Изделие 1 — витраж, 1 шт. — 244 378,00"), без технических полей
конфигуратора. Полная спецификация остаётся отдельным прикладываемым файлом — как сейчас, вручную,
вне генератора.

Проработка этого варианта в дизайн-сессии получилась не полностью готовой (по словам пользователя:
"отдельный случай вышел не совсем готовым"). Для MVP реализации это не блокер — просто не
пытаться автоматизировать генерацию приложения конфигуратора, только основной документ КП. Держать
в уме на будущее, если понадобится доработка именно этого сценария.

## Design tokens

- **Шрифты:** Inter (текст), JetBrains Mono (моно/цифры, опционально) — оба нужно **встраивать
  как base64 woff2** в HTML, не полагаться на системные шрифты контейнера (в Puppeteer/Chromium
  внутри LXC нет гарантии наличия кириллических шрифтов). Fallback: Arial/Helvetica.
- **Цвета:** нейтральная минималистичная палитра в OKLCH (ink/text/muted/line + 1 акцентный +
  accent-soft), без декоративных ярких элементов — тёмно-синяя шапка текущего generic-шаблона
  уходит.
- **Сетка/отступы (A4, печатные единицы):** поля 20мм сверху/снизу, 18мм слева/справа, 8мм
  между блоками. Текст тела 10.5pt/1.5, таблица 9.5pt с padding ячеек ~2.5×3мм, заголовок КП
  15pt/700, название компании 11pt/700, мелкий текст реквизитов 8pt приглушённый.

## Финальная структура данных

```
Template.data:
{
  company: {
    name, shortName, logo,           // logo — base64/путь, встраивается в PDF
    inn, kpp?, ogrn?,                // kpp/ogrn опциональны
    address, phone, email,
    bank?: { account, bankName, bik, corrAccount }  // весь блок опционален
  },
  signer: { fullName, position, signatureImage?, stampImage? },
  items: [{ name, unit, quantity, price }],  // позиции-по-умолчанию для шаблона
  terms: [...],
  footer
}

Proposal.data:
{
  number, date,
  recipient: { position, org, fullName },
  description,
  items: [{ section?, name, unit, quantity, price }],  // section — опционально
  validDays,
  vatNote
}
```

Важное отличие от текущей модели: у позиции появляется поле **`unit`** (единица измерения —
её сейчас нет вообще) и опциональное **`section`** (замена плоского списка на группировку).
Поле `description` у позиции в новой структуре не встречается — переносится на уровень `name`
+ возможно в `terms`/`footer`, если нужно что-то развёрнутое.
