# Phase 10C: PDF/Word/скан — расширение Level 0 (не реализуется сейчас, архитектура заранее)

> Вынесено из [PHASE_10B_level0_ingestion_plan.md](PHASE_10B_level0_ingestion_plan.md) по
> рекомендации раунда 3 технического ревью (`PHASE_10B_review_round3.md`, §8): раздел
> «Фаза 2» в документе финальной сверки перед сборкой сам дал две находки (I5, I6 раунда 3),
> будучи функционалом, который не реализуется в этом раунде. Вынесен как отдельный документ серии
> Phase 10, чтобы не смешивать «что собираем сейчас» и «куда это должно уметь расти» — при этом
> сохраняя архитектурную преемственность, которую пользователь явно потребовал зафиксировать до
> начала сборки xlsx/csv-пути.
>
> Не реализуется в текущем раунде. Единственное, что уже есть в 10B на этот счёт, — шаг 1b
> (проверка формата) и папка `unsupported/`, которые дают безопасное, явное поведение для
> файлов, описанных здесь, до тех пор, пока эта фаза не будет спроектирована в деталях и собрана.

## Почему это не просто «добавить .pdf в список расширений»

Оригинальная схема Уровня 0 (`PHASE_10_PRICE_CATALOG_PLAN.md`) с самого начала описывала «Extract»
как обработку текста документа **целиком** одним вызовом LLM, возвращающим массив позиций — не
построчный цикл, который построен в 10B под xlsx/csv (`Loop Over Items`, батч 25, по строкам
таблицы). Это два разных паттерна извлечения: 10B — «много маленьких строк, известная структура»,
10C — «один документ, свободный текст, структуру предстоит распознать». Вторая фаза добавляет
новый паттерн извлечения, не переделывает первый.

## Что уже готово к переиспользованию без изменений

Ключевое свойство дизайна 10B, ради которого стоило спроектировать эту часть заранее: таблица
`n8n_ingest_runs` и вся логика от шага 8 workflow #1 (10B) дальше — heartbeat (батч), resume
(включая retry упавших строк, I2 раунда 3), watchdog (#4), terminal-статусы, глобальный слот на
GPU (C3), папка `postponed/` (C1) — **format-agnostic**. `rows_total`, `rows_processed`,
`source_row` это просто целые числа, им всё равно, откуда взялась «строка»: из ячейки таблицы или
из индекса элемента в JSON-массиве, который вернула LLM за один проход по документу. Точка
расширения — узко в начале, где файл разбирается на «строки» (шаги 3-9 workflow #1 в 10B), а не
во всём пайплайне.

## Архитектура (проектируется сейчас, не реализуется)

1. После шага 1b («Проверка формата», 10B) ветка для `.pdf`/`.doc`/`.docx` (и, отдельно, скана —
   через OCR, модель для которого ещё не выбрана, `PHASE_10A_llm_infra_plan.md`) идёт не в
   `unsupported/`, а в свой путь извлечения.
2. Извлечение текста документа целиком (`Extract From File` для pdf; для docx может понадобиться
   отдельный узел/подход — не проверено, требует отдельного тестового документа). Для скана —
   сначала OCR, дальше тот же путь.
3. Один вызов LLM на весь текст документа (или несколько, если документ длинный — **чанкинг не
   решён, главный открытый вопрос этой фазы**, нужен реальный тестовый PDF/Word документ, чтобы не
   проектировать вслепую — тот же принцип, что уже применялся к xlsx в 10B: сначала реальные
   данные, потом дизайн) с JSON Schema «массив позиций» вместо построчной схемы шага 7 (10B).
4. Результат — массив `{source_work_name, unit, price, price_qualifier, confidence}` — дальше
   заводится в те же шаги 8-14 workflow #1 (10B: `Loop Over Items` по элементам массива вместо
   строк xlsx, heartbeat/ingest/resume/архивация без изменений), `source_row` = индекс элемента
   массива, а не номер строки xlsx (та же формула абсолютного индекса, что и C4 в 10B, только
   единица — не строка таблицы, а элемент результата LLM).

## Что нужно от пользователя, когда дойдём до этой фазы

Один реальный PDF или Word документ (старое КП или прайс поставщика в этом формате) для проверки —
так же, как реальный xlsx-прайс сейчас используется для калибровки построчного пути в 10B. Без
этого документа чанкинг (п.3 выше) не может быть спроектирован обоснованно — только предположениями.

## Что не входит сюда

OCR-путь (сканы) — отдельно зависит от выбора модели в `PHASE_10A_llm_infra_plan.md`, которая
на момент написания этого документа помечена «не начато». Пока модель не выбрана, скан-ветка не
проектируется даже на уровне архитектуры выше — только упомянута как существующая в списке форматов.
