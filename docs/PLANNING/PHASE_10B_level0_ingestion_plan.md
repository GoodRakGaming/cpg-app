## Контекст (для ревьюера без доступа к истории обсуждения)

### Что такое этот проект и зачем нужен Level 0
`commercial_proposal_generator` — внутреннее приложение компании-подрядчика (строительно-отделочные
работы) для генерации коммерческих предложений (КП) клиентам. Один из модулей, Phase 10, строит
«справочник цен» — базу знаний о реальных ценах на виды работ, собираемую из разных источников
(собственные старые КП, прайсы поставщиков, скан-копии, сайты конкурентов), чтобы при составлении
нового КП сотрудник видел подсказку «эта работа обычно стоит X₽» вместо ручного поиска в старых
файлах. Справочник наполняется через один и тот же входной API-эндпоинт независимо от источника
данных — `POST /api/price-catalog/ingest` (backend/src/routes/priceCatalog.js). При приёме каждой
позиции срабатывает внутренний сервис-«Библиотекарь» (backend/src/services/librarianService.js),
который через локальную LLM (Ollama, devstral:24b, отдельный сервер LXC 107 на том же Proxmox-хосте)
приводит вольное название работы к каноническому виду и категории, чтобы одинаковые по сути работы
из разных источников собирались в одну статистику цены, а не плодили дубли-синонимы.

`ingest` и Библиотекарь **уже полностью реализованы, задеплоены на прод и подтверждены рабочими**
сквозным тестом на реальных данных (12/12 кейсов, включая намеренные ловушки на слияние разных по
объёму работ и на неверную категоризацию) — это не предмет текущего ревью, это готовая, стабильная
часть системы, к которой планируемый n8n-пайплайн обращается как к чёрному ящику через HTTP.

Источников данных для наполнения справочника три уровня по возрастанию сложности (термины уровней
уже согласованы и зафиксированы в более раннем документе `docs/PLANNING/PHASE_10_PRICE_CATALOG_PLAN.md`,
не переоткрывать): Уровень 0 — сотрудник вручную кладёт документ в общую папку, дальше автоматика;
Уровень 1 — регулярный обход известных сайтов поставщиков/конкурентов по расписанию; Уровень 2 —
мониторинг рынка/новостей. **Этот план — только про Уровень 0.**

### Почему выбран именно n8n + Nextcloud
У владельца системы уже развёрнута и используется собственная инфраструктура на одном Proxmox-хосте:
Nextcloud, n8n (self-hosted, владелец уже умеет им пользоваться и подключать к нему ботов
Telegram/VK), Ollama на отдельном LXC с GPU. Никакого нового сервиса не заводим — n8n остаётся
лёгким оркестратором поверх уже готового `ingest`.

### Реальный тестовый документ
Прайс-лист поставщика «Альфа групп», xlsx, 545 строк, структурированная таблица (не скан — OCR не
требуется для этого документа). Реальные названия колонок пока не известны автору плана — донастройка
руками после первого тестового запуска.

Параллельно (не в этом плане, отдельная будущая задача) готовится «быстрый путь» — прямой скрипт
xlsx → `ingest` без LLM-извлечения, для сравнения по времени и качеству с этим пайплайном.

### Масштаб и ограничения ресурса
- Команда маленькая, доверенная, единицы-десятки человек.
- LLM-инфраструктура — **один** сервер Ollama с одной GPU, `devstral:24b`. Холодный прогрев после
  простоя замерян эмпирически: **110.9 секунд**. Таймаут HTTP-вызовов к Ollama — 180000 мс.
- `ingest` сам по себе делает **2 дополнительных вызова LLM на позицию** (категоризация +
  канонизация) — на каждую строку xlsx приходится **3 последовательных LLM-вызова**. Ожидание на
  545 строк — часы, не минуты (только Библиотекарь без извлечения давал ~93 минуты на 545×2 вызова).
- Прод — единственное окружение. Backend деплоится через `git push production main`
  (`docs/DEPLOYMENT.md`); n8n-workflow импортируется вручную в UI n8n, не через этот деплой.
- У автора плана **нет доступа** к n8n UI/API, Nextcloud UI/API, секретам — всё такое в разделе
  «Что делает пользователь сам».

## Как согласовывалась архитектура (не переоткрывать)
- «Одна папка = мгновенный триггер для всех» отклонено: случайный/чужой файл мог бы запустить
  многочасовой дорогой прогон без возможности отмены.
- Финальная защита — гибрид: обычный сотрудник видит только `На анализ/`, файл там ждёт до ночной
  автоматики (защита временем, офф-пик); прямой перенос в `queue/` в обход ожидания доступен
  только владельцу (защита правами — папка расшарена только на его аккаунт).
- План Б (`Manual`/`Schedule`) — страховка на случай, если webhook технически не сработал, не способ
  обойти защиту.
- Метрики — таблица в БД, а не файлы/только n8n Executions: заказчик прямо попросил удобство
  изучения статистики со временем (SQL-запросы, потенциальный будущий экран в дашборде).

## Раунд 2 — что изменилось (все находки приняты, не переоткрывать)

Полная модель состояний (claim-папка, глобальный слот, heartbeat, resume, terminal-статусы) закрыта
раундом 2 и подтверждена раундом 3 (9.5/10, возражений нет). Ниже — конспект решений, детали
механики (циклы, SQL, индексы) обновлены под раунд 3 в разделах ниже.

- **B1** heartbeat по `updated_at`, обновляется по ходу прогона; watchdog судит о зависании по
  `now() - updated_at > threshold`, не по `started_at`.
- **B2** тест №0 первым — подтвердить, что перемещение файла в `queue/` реально шлёт webhook, что
  кастомный заголовок доходит (раунд 3 добавил: и что события НЕТ на `move` **из** `queue/` —
  см. C1 ниже). **Пройден на проде** — механизм оказался не Nextcloud Flow (в этой версии его
  нет), а приложение `webhook_listeners` через OCS API, подробности в разделе «Триггеры» ниже.
- **B3** глобальный слот на одну GPU — таблица `n8n_ingest_runs` (SQL обновлён под C3 ниже).
- **B4** `Error Trigger` не ловит обработанные IF-ветки — ветка ошибки sub-workflow #1 сама шлёт
  Telegram-алерт; `Error Trigger` (#5) — только для настоящих непредвиденных падений.
- **B5** `archive/<YYYY-MM-DD>/<файл>` — защита от коллизии имён; поиск активного прогона по
  `nextcloud_file_id`, с фолбэком (раунд 3 уточнил приоритет — см. I3 ниже).
- **I1** resume по `rows_processed` (обновлён под C2/C4 — абсолютный индекс, не `$itemIndex`).
- **I2** узкий `GET /ingest-runs/active` под ingest-ключом для watchdog; полный `GET /ingest-runs`
  под JWT.
- **I3** watchdog, не нашедший запись прогона для файла в `processing/` — возвращает файл (в
  раунде 3 — в `postponed/`, не в `queue/`, см. C1) + алерт.
- **I4** терминальный статус `completed_with_errors` — одна битая строка не отправляет весь файл
  в `errors/`.
- **I5** `source_detail` не хардкодится, читается из `!! ЗАПОЛНИ`; `run_id` в `raw_extraction`.
- **I6** счётчики `rows_success`/`rows_failed` считаются один раз через `Merge` + `Code`, не
  императивно.
- **I7** `keep_alive: "30m"` в каждом вызове Ollama.
- **I8** claim: `404`/`409` → тихий выход; остальные ошибки → `Error Trigger`.

## Раунд 3 — блокеры (обязательны до сборки)

### 🔴 C1 — откат claim и восстановление кормили бы тот же webhook

Три пути (откат claim при 409 глобального слота; watchdog на `running`; watchdog без записи
прогона, I3) заканчивались перемещением файла обратно в `queue/` — а это то же самое событие
Flow, что и обычное появление файла там. Итог без исправления — самоподдерживающийся busy-loop на
всё время занятости слота (часы), не ловится ни одним из тестов 0-18, каждое исполнение — success,
алерт не сработает.

**Решение:** отдельная папка `postponed/`, на которую Flow-правило не настроено — повторного webhook
нет. Все три пути восстановления ведут в неё, не в `queue/`. План Б (#4) сканирует `postponed/`
наравне с `queue/`. Тест №0 расширен: после подтверждения события на `move` **в** `queue/`
проверяется, что события нет на `move` **из** `queue/` (если механизм окажется «любое
изменение», а не «файл добавлен» — потребуется другой способ сигнализировать mv, решается на месте
по факту теста №0).

### 🔴 C2 — нужен явный цикл: `Loop Over Items` (батч 25), а не «нода за нодой»

n8n по умолчанию не делает построчный цикл: `Extract From File` отдаёт все items разом, каждая
следующая нода отрабатывает весь массив целиком, прежде чем управление идёт дальше. Без явного
цикла heartbeat выполнится один раз в конце многочасового прогона (что убивает и B1, и resume I1),
а ingest начнётся только после того, как ВСЕ извлечения закончены (при падении на середине — в БД
не будет ни одной записи, хотя LLM отработала сотни строк).

**Решение:** явный узел `Loop Over Items` (Split In Batches), размер батча 25, охватывающий шаги
6-11 (см. workflow #1 ниже). Heartbeat — в конце каждой итерации батча (не «каждые 25 строк» как
формулировка частоты, а «в конце итерации» как структурная точка — I1, ниже).

Калибровочный тест увеличен с ~25 до **~60 строк** (2.5 батча) — иначе тест проходит одинаково и
с циклом, и без него, и первый тест, который увидел бы разницу, — это шестичасовой прогон на 545
строках.

### 🔴 C3 — партиальный уникальный индекс работал не как глобальный слот

```sql
-- было (раунд 2, неверно):
CREATE UNIQUE INDEX n8n_ingest_runs_single_active
  ON n8n_ingest_runs (status)
  WHERE status IN ('running', 'ingest_completed_archive_pending');
```

Уникальность в Postgres действует на значение индексируемого столбца, а не на всё множество строк,
покрытых условием `WHERE`. `'running'` и `'ingest_completed_archive_pending'` — разные значения,
поэтому одновременно могла существовать одна строка каждого вида — по счастливой случайности это не
било по GPU (второе состояние GPU не занимает), но было записано с неверным обоснованием, и вдобавок
`PATCH` перехода `running → ingest_completed_archive_pending` мог упасть на нарушении уникальности,
если первая строка того же статуса зависла (напр. Nextcloud недоступен) — успешный четырёхчасовой
прогон падал бы на последнем шаге.

**Решение:**

```sql
CREATE UNIQUE INDEX n8n_ingest_runs_single_active
  ON n8n_ingest_runs (status)
  WHERE status = 'running';
```

Слот занимает только `running` (защищает GPU); переход в `ingest_completed_archive_pending` —
штатное освобождение слота, `PATCH` не конфликтует.

**Плюс страховка от застрявшего слота:** `POST /ingest-runs`, отдавая 409, возвращает в теле
`{blocked_by: {run_id, source_filename, updated_at}}`. Workflow #1 при 409 сравнивает
`now() - updated_at` с порогом watchdog; если блокирующий прогон давно не подавал признаков жизни —
Telegram-алерт «слот занят зависшим прогоном X с такого-то времени» вместо тихого отката в
`postponed/`. Без этого — если исполнение, державшее `running`, умерло, а watchdog ещё выключен
(до калибровки порога, B1) — каждый следующий файл получает 409 молча, и система полностью
останавливается без единого алерта.

### 🔴 C4 — `source_row` должен быть абсолютным индексом, не `$itemIndex`

Две проблемы: (а) `$itemIndex` 0-based, не знает про строку заголовков — строка 137 в Excel
приедет как `source_row: 135`; (б) при `Loop Over Items` (C2) `$itemIndex` считается заново на
каждой итерации батча — `source_row` пойдёт `0..24, 0..24, 0..24`, что ломает поиск исходной строки,
`error_summary` и, критично, **resume** (сравнение `source_row <= rows_processed` даёт молча
неверный результат — часть строк теряется, часть обрабатывается дважды).

**Решение (раунда 3, уточнено в разделе «Раунд 4» ниже — D3):** абсолютный индекс, `+2` —
смещение на строку заголовка при одной строке заголовков (зафиксировать это соглашение явно, если
заголовков больше одной строки — донастроить при первом тестовом запуске). Раунд 4 нашёл, что
вычислять его нужно **до** resume-фильтра, а не внутри цикла по формуле с номером итерации — иначе
при возобновлении прогона индекс считается от позиции в уже отфильтрованном массиве и не совпадает
с реальным номером строки файла; актуальная формула и место вычисления — в разделе D3.

## Раунд 3 — важное (закрыто)

- **I1 (heartbeat после ingest, не после извлечения).** Heartbeat перенесён на конец итерации
  батча — **после** шага 11 (когда по каждой строке батча известен `ok: true/false`), не между
  Ollama и ingest. Иначе исполнение, упавшее между извлечением и записью в БД, оставляет
  `rows_processed` продвинутым на строки, которых в `price_catalog` нет — resume их пропустит.
- **I2 (упавшие строки при resume — принято полное решение, не документированный шорткат).**
  `resumed_from_run_id UUID NULL` в таблице — связывает возобновлённый прогон с предыдущим для
  сборки сводки по файлу через SQL. При resume строки, завершившиеся `ok: false` в предыдущем
  прогоне (номера — в его `error_summary`), **не пропускаются** наравне с успешными: условие
  пропуска — `source_row <= rows_processed AND source_row NOT IN (упавшие_строки_предыдущего_прогона)`.
  `trigger_type: 'watchdog'` помечает именно такие возобновлённые прогоны (см. мелочи раунда 2/3
  ниже — раньше это значение не использовалось нигде).
- **I3 (`nextcloud_file_id` — не проверено, откуда берётся).** `move`/`List a folder` в n8n Nextcloud
  ноде не гарантированно отдают `oc:fileid` без явного PROPFIND. Тест №0 расширен: проверить,
  приходит ли `oc:fileid` в ответе `move`/в payload webhook. Если недоступен без ручного PROPFIND —
  **фолбэк по `source_filename` принимается как основной путь**, не как запасной, и это фиксируется
  в плане. Добавлен индекс по `source_filename` в миграцию (был только по `nextcloud_file_id`,
  который может оказаться всегда `NULL`).
- **I4 (порог watchdog занижен на порядок).** `updated_at` обновляется не «раз в строку», а раз в
  батч. `threshold = k × (размер батча) × (максимальное время на строку)`, `k ≥ 2` — записана
  формула, не число, чтобы пересчитывалась при изменении размера батча.
- **I5 (`.csv` в списке поддерживаемых, но не реализован).** Убран из списка «реализовано» в шаге
  1b — для Level 0 сегодня существует ровно один реальный документ, и он xlsx. `.csv`
  по-прежнему корректно распознаётся workflow #3 (I6) и уходит в `unsupported/`, если
  встретится — не требует отдельной ветки обработки.
- **I6 (фильтр ночной автоматики — один список, не два разных).** Workflow #3 фильтрует **по всем**
  форматам Level 0 (`.xlsx`, `.csv`, `.pdf`, `.doc`, `.docx`) при обходе `На анализ/` — иначе PDF/Word
  никогда не покидают `На анализ/` и ветка Фазы 2 (10C) на ночном пути мертва. Мусорные файлы
  (`.DS_Store`, `Thumbs.db` и т.п.), не входящие ни в один список, остаются в `На анализ/` молча
  (не мешают, не блокируют — осознанное решение, не автоматическая уборка чужих файлов).
- **I7 (`finished_at` — было записано двумя способами в разных местах документа).** `finished_at`
  выставляется **только** при терминальных статусах `completed`/`failed`/`completed_with_errors` —
  убран из `PATCH` шага 13 в ветке `ingest_completed_archive_pending` (там `finished_at` рано,
  архивация ещё не подтверждена).

## Раунд 3 — мелкое (закрыто)

- Индекс по `source_filename` в миграции — добавлен (I3).
- **Алерт «формат не поддерживается» — один агрегированный, не по одному на файл.** Workflow #3
  теперь сам разделяет файлы `На анализ/` по спискам (I6) и **напрямую** переносит нераспознанные
  форматы в `unsupported/` с одним общим Telegram-сообщением (список файлов), не вызывая
  workflow #1 для них вовсе — GPU-слот не трогается, запись прогона не создаётся, шаг 1b для этих
  файлов не выполняется. Шаг 1b в workflow #1 остаётся как защита на пути ручного переноса
  владельцем (2б) и плана Б — там файлы единичные, накопления алертов не бывает.
- `onError: continue` на Telegram-узле в ветке ошибки шага 13 (B4) — падение самого уведомления
  (Telegram недоступен) не должно ронять исполнение, которое по сути уже завершилось.
- `trigger_type: 'watchdog'` теперь используется — помечает возобновлённые прогоны (I2), а не
  прогоны, которые watchdog «завёл» (watchdog прогонов не заводит, он только возвращает файлы).
- Тест 17 (размер execution) расширен: смотреть и на **количество** исполнений workflow #2 за
  период, не только на размер одного — с учётом C1 это отдельный сигнал.

## Раунд 4 — блокеры (обязательны до сборки)

C1-C4 (раунд 3) подтверждены верными каждый по отдельности. Три находки ниже — недоведённые стыки
между ними, все три сходятся в одном механизме: resume. Без исправлений он не стартует (D1), не
находит файл (D2) и писал бы неверные координаты, если бы всё-таки стартовал (D3).

### 🔴 D1 — зомби-строка `running` навсегда блокирует слот, resume не запускается

Watchdog (см. #4 ниже), эвакуируя файл с зависшим прогоном в `postponed/`, двигал файл, но не
трогал его запись в `n8n_ingest_runs` — она оставалась `running` навсегда. Слот (C3) занят этой
строкой без ограничения по времени: **любой** следующий файл (не только этот же) получает 409 и
откатывается, пока кто-то не поправит статус руками в `psql`. Заявленный механизм автоматического
восстановления фактически не восстанавливает систему сам.

**Решение:**
1. Новый терминальный (для прогона, не для файла) статус **`abandoned`** — отдельный от `failed`:
   `failed` значит «файл обработан, результат плохой» (файл лежит в `errors/`); `abandoned` значит
   «прогон брошен, файл будет продолжен» — разные судьбы, разная семантика в статистике.
2. Watchdog, перенося файл с прогоном `running` в `postponed/`, **тем же действием** делает
   `PATCH {status: 'abandoned'}` этой записи — освобождает слот и оставляет честный след. То же —
   в ветке «записи нет» (I3 раунда 3) ничего PATCH'ить не нужно, записи и так нет.
3. `finished_at` для `abandoned` не ставится — прогон не завершился, он брошен, в аналитику
   длительности попадать не должен (тот же класс решения, что I7 раунда 3).
4. **Порядок resume-детекции меняется на GET-перед-POST**, что заодно устраняет и «знание из
   будущего» на шаге 2 (раньше `resumed_from_run_id`/`trigger_type: 'watchdog'` записывались туда
   же, до того как шаг 5 успевал это выяснить):
   ```text
   шаг 2 (новый порядок): GET {{RUNS_URL}}/ingest-runs/active?filename=...  — активный прогон по файлу
       ├─ нет → POST {status: 'running'} как обычно
       ├─ есть, и stale (updated_at старше threshold) →
       │     PATCH {status: 'abandoned'} ему →
       │     POST {status: 'running', resumed_from_run_id, trigger_type: 'watchdog'}
       └─ есть, и живой → гонка, откатить claim в "postponed/", выйти без ошибки
   ```

### 🔴 D2 — claim захардкожен на `queue/`, файлы из `postponed/` необрабатываемы

Шаг 1 (claim) был жёстко привязан к одному пути (`queue/<файл> → processing/<файл>`). Но план
Б (#4) сканирует уже **две** папки — `queue/` и `postponed/` (C1). Для файла, найденного в
`postponed/`, claim пытался переместить `queue/<файл>`, которого там нет → `404` → ветка I8
«тихий выход, штатный проигрыш гонки» — которая здесь честно маскирует баг под норму. Итог: любой
файл, хоть раз прошедший через `postponed/` (то есть каждый файл, столкнувшийся с 409 или
watchdog'ом), молча выводится из оборота навсегда.

**Решение:** sub-workflow #1 принимает на вход не только имя файла, но и **`source_folder`**
(`queue/` | `postponed/`), claim делает `<source_folder>/<файл> → processing/<файл>`. #2
(webhook) всегда передаёт `queue/` (Flow слушает только её); #4 передаёт ту папку, в которой
файл реально найден при сканировании. Откат по 409 (шаг 2) по-прежнему всегда ведёт в `postponed/`
независимо от источника — это не меняется.

### 🔴 D3 — `source_row` считался после resume-фильтрации — писал бы неверные номера строк

Порядок был: шаг 5 (resume) выбрасывает уже обработанные строки → шаг 6 (цикл) вычисляет
`source_row` по позиции элемента **в уже отфильтрованном массиве**. При первичном прогоне позиция
в файле и в массиве совпадают, всё верно. При возобновлении — нет: если первый прогон умер на
строке 300, resume выбрасывает строки 2-300, и первая строка, вошедшая в цикл (реально строка 301
файла), получает `source_row = 2` (итерация 0, `$itemIndex` 0). Ломается `raw_extraction`,
`error_summary`, и по кругу — resume следующего уровня, если и этот прогон прервётся: его
`rows_processed` описывает уже несуществующую систему координат.

**Решение — перенести вычисление на шаг раньше цикла и сделать его независимым от фильтрации:**
1. `source_row` вычисляется **один раз, сразу после шага 4** (`Extract From File`), по позиции в
   **сыром** (нефильтрованном) массиве: `$itemIndex + 2`. Дальше это неизменное свойство item,
   которое фильтр (шаг 5) и батчи (шаг 6) просто переносят вместе со строкой. Формула с номером
   итерации из раунда 3 (C4) была компенсацией того, что вычисление стояло слишком поздно —
   больше не нужна.
2. Heartbeat (шаг 11, конец итерации батча) пишет `rows_processed = max(source_row)` обработанного
   батча, а не `(номер_итерации+1) × 25` — единственная формулировка, переживающая фильтрацию, и
   она же не даёт `rows_processed` превысить `rows_total` на последнем неполном батче.
3. Resume при цепочке из нескольких прерываний берёт границу как `max(rows_processed)` по всей
   цепочке `resumed_from_run_id` (доступна тривиальным запросом после D1), а не только по
   последнему прогону — иначе второй resume после второй смерти видит только хвостовой прогресс.

Узел `!! ЗАПОЛНИ` внутри цикла остаётся (сбор `row_text` из колонок — его законное место), но
больше не вычисляет `source_row`.

## Раунд 4 — важное

- **E1 (`error_summary` — конфликт ролей).** Resume (I2 раунда 3) читал номера упавших строк из
  `error_summary`, но эта колонка намеренно ограничена ~20 уникальными ошибками (I6 раунда 2) —
  при более чем ~20 упавших строках resume молча принял бы строки 21+ за успешные. Плюс парсинг
  номеров из свободного текста — хрупкая операция. **Решение:** отдельная колонка `failed_rows
  INTEGER[]` — пишется тем же heartbeat-PATCH, читается resume как есть, без парсинга;
  `error_summary` остаётся человекочитаемым и остаётся ограниченным — роли разведены.
- **E2 (гейт калибровки перекрывал не только watchdog, но и всю очередь).** `Schedule Trigger`
  workflow #4 был единым выключателем на обе ветки — из-за этого до калибровки порога переставала
  ходить по расписанию не только watchdog-ветка (ей это и нужно), но и обычная очередь, то есть
  файлы, откатившиеся в `postponed/` по 409, лежали бы там до ручного запуска — именно в тот период
  (первые запуски), когда 409 наиболее вероятны. **Решение:** один `Schedule Trigger` с первого
  дня; гейт «порог задан?» стоит отдельным IF только перед watchdog-веткой (порог лежит в Config,
  пока пуст — ветка не выполняется), очередная ветка ходит всегда — она и так защищена claim'ом и
  слотом.
- **E3 (тест 12 смешивал два разных сценария).** Разбит на 12а (файл с одной битой строкой
  доходит до `completed_with_errors`, архив, алерт — resume для терминального прогона не
  существует и не должен, догрузка упавших строк — по алерту вручную) и 12б (прогон **прерывается
  до завершения**, resume повторяет и необработанный хвост, и упавшую строку из уже пройденной
  части батча — это прямая проверка D3+E1+I2 разом, самый ценный тест плана; выполняется на
  калибровочных 60 строках, где прервать исполнение дёшево).

### Триггеры (три независимых пути, один общий обработчик)
1. **Мгновенный (подтверждено тестом №0 на проде)** — не «Nextcloud Flow» в классическом
   понимании (эта версия Nextcloud такого UI для «Request URL» не имеет), а встроенное
   приложение **`webhook_listeners`** (`occ app:enable webhook_listeners`), подписка регистрируется
   один раз через OCS API (`docs/PLANNING/n8n_workflows/setup_nextcloud_webhook.sh`) на событие
   `OCP\Files\Events\Node\NodeRenamedEvent` — **широко, без `eventFilter`** (regex-фильтр по пути
   с кириллицей на этой версии `webhook_listeners` не матчит, потрачено много circles на попытки
   его починить — не переоткрывать). Фильтрация «это наша папка» сделана внутри n8n, workflow #2,
   узел «Это наша папка?», по `event.target.path`. Два практических нюанса, тоже подтверждённые
   тестом №0: (а) `allow_local_remote_servers` должен быть включён в Nextcloud (`occ config:system:set
   allow_local_remote_servers --value=true --type=boolean`) — иначе исходящие запросы `webhook_listeners`
   на внутренний LAN-адрес n8n блокируются встроенной защитой от SSRF молча (job в занимает очередь,
   «finished», но ничего не долетает — легко принять за баг фильтра, им не являясь); (б) доставка
   идёт через фоновую cron-задачу, по умолчанию раз в ~5 минут — для менее заметной задержки нужен
   отдельный воркер (`occ background-job:worker -t 60 "OCA\WebhookListeners\BackgroundJobs\WebhookCall"`
   как systemd-сервис, несколько экземпляров), не поднят на момент теста №0, замерить отдельно.
   `target.path` для `NodeRenamedEvent` отражает **новое** расположение файла — уход **из**
   `queue/` даёт `target.path` без этой папки и не проходит проверку «Это наша папка?» в n8n
   (C1 закрыт этим же способом, без опоры на несработавший `eventFilter`).
2. **Ночная автоматика** — workflow #3, `Schedule Trigger` (например, 04:00) → фильтр по всем
   форматам Уровня 0 (`.xlsx`, `.csv`, `.pdf`, `.doc`, `.docx` — I6) → реализованные (`.xlsx`,
   после I5 только он) идут в `queue/`; нераспознанные форматы уходят напрямую в
   `unsupported/` с одним агрегированным Telegram-алертом (не через workflow #1, GPU-слот
   не занимается).
3. **План Б / watchdog** — `Manual Trigger` (всегда доступен) + `Schedule Trigger` (интервал —
   решить на этапе сборки; watchdog-ветка выключена до калибровки порога, см. I4) → одна и та же
   логика «пройтись по `queue/` и `postponed/`, обработать; пройтись по `processing/`,
   разобраться с зависшими по `updated_at`».

Все три ведут в один переиспользуемый **sub-workflow** «Обработать файл прайса» (DRY).

## n8n workflows (5 штук, сквозная нумерация)

### #1 — «Обработать файл прайса» (sub-workflow, ядро)
Вход: путь к файлу в Nextcloud + **`source_folder`** (`queue/` | `postponed/` — D2, кто вызвал
и откуда взял файл).
0. `Set` **«Config»** — `OLLAMA_URL`/`INGEST_URL`/`RUNS_URL`/`BATCH_SIZE=25`/`WATCHDOG_THRESHOLD`
   (пусто до калибровки — E2), остальные ноды ссылаются на него.
1. **Claim** — Nextcloud `move`: `{{source_folder}}/<файл> → processing/<файл>` (D2 — берётся из
   входного параметра, не захардкожено на `queue/`; иначе файлы, найденные в `postponed/`,
   получали бы `404` на несуществующем пути и тихо выпадали из обработки под видом штатного
   проигрыша гонки). IF по HTTP-коду ошибки (I8): `404`/`409` → тихий выход, штатный проигрыш
   гонки; иначе → ошибка исполнения (уйдёт в `Error Trigger`, workflow #5).
1b. **Проверка формата (запасной путь на случай ручного переноса — основной путь через #3, см.
   выше)** — расширение файла сверяется со списком реализованных (`.xlsx`, I5). Не реализовано
   → move `processing/ → unsupported/` + Telegram-алерт «формат X пока не реализован (см.
   10C)», стоп — **до** создания записи прогона, не занимает глобальный GPU-слот.
2. **Найти/создать запись прогона (D1 — GET перед POST, не сразу POST):**
   - `GET {{RUNS_URL}}/api/price-catalog/ingest-runs/active?filename=...` — есть ли уже активный
     (`running`) прогон по этому файлу.
   - **Нет активного** → `POST .../ingest-runs {source_filename, nextcloud_file_id, trigger_type,
     status: 'running'}` как обычно. **IF статус 409** (глобальный слот занят другим файлом, C3) —
     читать `blocked_by` из тела ответа; если `now() - blocked_by.updated_at` больше
     `WATCHDOG_THRESHOLD` — Telegram-алерт «слот занят зависшим прогоном» (C3, страховка); в любом
     случае откатить claim в **`postponed/`** (не в исходную `source_folder` — C1), выйти без
     ошибки.
   - **Есть активный, и он stale** (`updated_at` старше `WATCHDOG_THRESHOLD`, то есть исполнение,
     которое его вело, мертво) → `PATCH {status: 'abandoned'}` этой записи (D1 — освобождает слот
     C3, не даёт зомби-строке блокировать все последующие файлы навсегда), затем `POST
     {status: 'running', resumed_from_run_id: <id найденной записи>, trigger_type: 'watchdog'}`.
   - **Есть активный, и он живой** → настоящая гонка (два триггера почти одновременно) — откатить
     claim в `postponed/`, выйти без ошибки, как и в ветке 409.
   - Сохранить `run_id` для дальнейших шагов.
3. Nextcloud `download` файла из `processing/`.
4. `Extract From File` (`xlsx`) — 1 item = 1 строка (проверить тестом №1). **Если `rows_total =
   0`** — сразу `PATCH {status: 'failed', error_summary: 'пустой файл'}`, move в `errors/`, алерт,
   стоп. Иначе `PATCH {rows_total}`. **Сразу здесь, до resume-фильтра и до цикла (D3), вычислить
   `source_row = $itemIndex + 2`** для каждого item по позиции в этом сыром массиве (`+2` —
   смещение на строку заголовка при одной строке заголовков; донастроить при первом запуске, если
   заголовков больше). Дальше `source_row` — неизменное свойство item, переживающее и фильтр, и
   батчи.
5. **Проверка resume (I1/I2/D3)** — если для этого `nextcloud_file_id` (или `source_filename`,
   фолбэк — I3) есть цепочка прогонов через `resumed_from_run_id` (доступна после D1), взять
   `rows_processed = max(rows_processed)` по всей цепочке и `failed_rows` (E1, отдельная колонка,
   не парсинг `error_summary`) последнего прогона цепочки: пропустить строки с `source_row <=
   rows_processed`, **кроме** строк, перечисленных в `failed_rows` (не теряются молча). `resumed_
   from_run_id`/`trigger_type: 'watchdog'` уже установлены на шаге 2 — здесь только фильтрация.
6. **`Loop Over Items`** (Split In Batches, `BATCH_SIZE=25`) — открывает цикл, охватывающий шаги
   6-11 (C2). Внутри итерации:
   - **Узел, который донастраивает пользователь** (`!! ЗАПОЛНИ`) — собрать `row_text` из реальных
     колонок xlsx + `source_type` (подтвердить/поправить `'supplier'`) + имя поставщика для
     `source_detail` (не хардкод). `source_row` уже вычислен на шаге 4 (D3) — здесь ничего не
     пересчитывать.
   7. `HTTP Request` → Ollama `POST /api/generate`, `format` = JSON Schema `{source_work_name, unit,
      price, price_qualifier, confidence}`, **`keep_alive: "30m"`** (I7 раунда 2) в теле,
      `timeout: 180000`, **Retry On Fail** включено (2-3 попытки).
   8. `Set` — payload под `ingestPriceCatalogSchema` (`backend/src/validators.js:320-356`):
      `source_work_name, unit, price, price_qualifier, confidence, source_type, source_detail,
      raw_extraction: {snippet: row_text, source_row, run_id}`.
   9. `HTTP Request` → `POST {{INGEST_URL}}/api/price-catalog/ingest`, `X-API-Key` (пользователь
      вписывает сам). Retry On Fail для транспортных ошибок; без retry для 400/401.
   10. **IF** по результату шага 9 → пометить item `ok: true/false` + текст ошибки + `source_row`
       (не накапливать счётчик императивно — раунд 2 I6).
   11. **Heartbeat, конец итерации батча** (I1 раунда 3 — не «между Ollama и ingest», а здесь):
       `Merge` успех/ошибка веток текущего батча → `PATCH {rows_processed: max(source_row) этого
       батча, updated_at, failed_rows: (накопленный массив source_row с ok:false — E1)}`.
   Цикл возвращается к следующему батчу, пока items не кончатся.
12. После цикла — финальный `Code`: посчитать `rows_success`/`rows_failed`/`error_summary` по
    всем батчам (первые ~20 уникальных ошибок + счётчики повторов, не безлимитный `TEXT`).
13. **Итог:**
    - `rows_success === 0` (весь файл провалился) → `PATCH {status: 'failed', ...}`, move
      `processing/ → errors/`, Telegram-алерт из этой же ветки (B4 — не полагаться на Error
      Trigger; `onError: continue` на Telegram-узле, см. мелочи), стоп.
    - `rows_failed > 0` и `rows_success > 0` → `PATCH {status: 'completed_with_errors',
      rows_success, rows_failed, error_summary, finished_at}` (I7 — здесь `finished_at` уместен,
      это терминальный статус), Telegram-алерт со списком неудачных строк, **продолжить** к
      архивации (не в `errors/`).
    - Все строки успешны → `PATCH {status: 'ingest_completed_archive_pending', rows_success}`
      **без** `finished_at` (I7 — не терминальный статус, архивация ещё не подтверждена).
14. Nextcloud `move` файла в `archive/<YYYY-MM-DD>/` (B5). При успехе — финальный `PATCH {status:
    'completed', finished_at}` (или остаётся `completed_with_errors`, если пришли из этой ветки
    шага 13, `finished_at` уже проставлен там).

### #2 — «Триггер: мгновенный (webhook)»
`Webhook Trigger` → проверка shared-secret заголовка (401 при несовпадении) → распарсить путь
(payload не доверенный — файл/расположение/тип перепроверяются внутри #1, шаг «Claim») →
`Execute Workflow` (#1, `trigger_type: 'webhook'`, `source_folder: 'queue/'` — D2, Flow слушает
только эту папку, других источников у этого триггера не бывает).

### #3 — «Ночная автоматика: На анализ → queue»
`Schedule Trigger` (04:00) → Nextcloud `List a folder` на `На анализ/` → разбить по трём спискам
(I6): реализованные (`.xlsx`) → `move` в `queue/` (подхватывается webhook #2 для каждого файла
независимо — конкурентность по GPU решается на уровне #1/шаг 2, не здесь); нераспознанные форматы
Уровня 0 (`.csv`, `.pdf`, `.doc`, `.docx`) → `move` напрямую в `unsupported/`, **один**
агрегированный Telegram-алерт со списком (не по файлу — мелочи раунда 3); остальное (`.DS_Store`,
`Thumbs.db` и т.п.) — остаётся в `На анализ/` без действия. Перед переносом реализованных файлов —
Telegram-уведомление со списком того, что сегодня ночью будет обработано (раунд 2, M6).

### #4 — «Триггер: план Б / watchdog»
`Manual Trigger` (всегда) + **один** `Schedule Trigger`, активный с первого дня (E2 — раньше весь
`Schedule Trigger` был выключен до калибровки порога, из-за чего до неё не ходила по расписанию и
безопасная «обычная очередь», не только watchdog). Две ветки:
- **Обычная очередь** (без гейта — защищена claim'ом и слотом, работает с первого дня): `List a
  folder` на `queue/` **и `postponed/`** (C1) → `Execute Workflow` (#1, `trigger_type:
  'schedule'`/`'manual'`, `source_folder` = та папка, где файл реально найден — D2) на каждый файл,
  которого там ещё нет в `processing/`.
- **Watchdog** (за отдельным IF «`WATCHDOG_THRESHOLD` задан?» — E2, пока порог не откалиброван,
  ветка не выполняется даже при сработавшем Schedule): `List a folder` на `processing/` → для
  файлов без активности дольше `threshold = k × BATCH_SIZE × (максимальное время на строку)`,
  `k ≥ 2` (I4), по `updated_at` — смотрит в таблице прогонов по `nextcloud_file_id`/
  `source_filename` (I3): `ingest_completed_archive_pending` → повторить только move в архив;
  `running` → move файла в `postponed/` (C1) **и `PATCH {status: 'abandoned'}` этой записи
  прогона** (D1 — освобождает глобальный слот; без этого шага следующий прогон того же файла
  получил бы 409 от собственного мёртвого предшественника и снова откатился бы в `postponed/`),
  новый прогон при подхвате получит `resumed_from_run_id`/`trigger_type: 'watchdog'` через шаг 2
  workflow #1 (D1); **запись не найдена** → move в `postponed/` + алерт (PATCH не нужен — записи и
  так нет).

### #5 — «Оповещение об ошибках» (Error Trigger)
`Error Trigger` → сообщение (workflow, файл, строка, ошибка) → Telegram/VK. Используется для
настоящих непредвиденных падений исполнения — обработанные бизнес-ошибки (частичный/полный сбой
файла) шлют алерт сами из #1 (B4). **Выставить как «Error Workflow» у всех пяти workflow** —
по умолчанию не выставлено ни у одного.

CREATE TABLE n8n_ingest_runs (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  source_filename     VARCHAR(500) NOT NULL,
  nextcloud_file_id    VARCHAR(64),                -- I3: может остаться всегда NULL, см. индекс ниже
  resumed_from_run_id  UUID REFERENCES n8n_ingest_runs(id),  -- I2: связь возобновлённого прогона
  trigger_type        VARCHAR(20) NOT NULL,        -- 'webhook' | 'schedule' | 'manual' | 'watchdog'
  status              VARCHAR(40) NOT NULL,        -- 'running' | 'ingest_completed_archive_pending'
                                                    -- | 'completed' | 'completed_with_errors' | 'failed'
                                                    -- | 'abandoned' (D1: мёртвый прогон, слот освобождён,
                                                    -- файл будет продолжен — не то же самое, что 'failed')
  rows_total          INTEGER,
  rows_processed       INTEGER DEFAULT 0,          -- heartbeat пишет max(source_row) батча (D3), не
                                                      -- (итерация+1)×batch_size — переживает resume-фильтр
  rows_success         INTEGER DEFAULT 0,
  rows_failed          INTEGER DEFAULT 0,
  failed_rows           INTEGER[],                  -- E1: машиночитаемый список source_row с ok:false,
                                                      -- пишется heartbeat'ом, читает resume — не парсит
                                                      -- error_summary (тот ограничен ~20 записями)
  error_summary        TEXT,                        -- человекочитаемая сводка, ограничена ~20 уникальными
                                                      -- ошибками + счётчики повторов (не источник для resume)
  started_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at            TIMESTAMPTZ NOT NULL DEFAULT now(),  -- обновляется в конце итерации батча (I1)
  finished_at           TIMESTAMPTZ                 -- только completed/failed/completed_with_errors —
                                                      -- не ingest_completed_archive_pending (I7), не
                                                      -- abandoned (D1, прогон не завершился, он брошен)
);

CREATE UNIQUE INDEX n8n_ingest_runs_single_active           -- C3: одно значение, не IN (...)
  ON n8n_ingest_runs (status)
  WHERE status = 'running';

CREATE INDEX n8n_ingest_runs_status_started_idx              -- watchdog ходит этим запросом
  ON n8n_ingest_runs (status, started_at DESC);

CREATE INDEX n8n_ingest_runs_file_id_idx ON n8n_ingest_runs (nextcloud_file_id);
CREATE INDEX n8n_ingest_runs_filename_idx ON n8n_ingest_runs (source_filename);  -- I3: основной путь,
                                                                                   -- если file_id NULL
